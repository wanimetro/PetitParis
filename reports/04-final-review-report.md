## 0. 중간발표용 요약 — 지금까지 한 것 / 프로젝트 소개

### 프로젝트 한 줄
> **"사람 발밑 12cm에서 본 파리."** 작은 쥐가 되어 카페 테라스 → 빵집 앞 → 골목 → 센강 → 비스트로 주방 식탁 위 치즈까지, 사람 발걸음을 피해 숨고 달리는 3~5분짜리 Quest 3 VR 게임.

### 핵심 아이디어
- **스케일 자체가 경험이다**: 세상을 키우지 않고 플레이어 추적 공간만 0.1배로 줄였다(방식 A). 머리 회전은 1:1이고 머리 이동과 IPD는 1/10이다 → 의자가 건물처럼, 사람 신발이 자동차처럼 보인다.
- **숨기와 소리로 하는 긴장감**: 발소리(3D), 발 그림자, 착지 예고 원으로 위험을 미리 알리고, 의자·벤치·팔레트 밑에 숨는다. 카메라를 흔드는 연출은 쓰지 않는다.

### 지금까지 구현한 것 (코드 기준)
| 영역 | 구현 내용 |
|---|---|
| XR 기반 | OpenXR + XRI 3.6.1 리그, 쥐 눈높이 자동 캘리브레이션(Quest 재중심 대응), PC 대체 모드(마우스·WASD) |
| 이동 | 단일 이동 경로(LocomotionProvider → CharacterController), 걷기·달리기·질주·점프·웅크리기, 30° 스냅 회전, 질주 비네트, 체감 속도 상한 |
| 위험 | 절차적으로 걷는 보행자 4명(웨이터·셰프), 왕복 자전거, 차양에서 굴러떨어지는 바게트, 빗자루 웨이터 추격 이벤트 |
| AI 반응 | 사람이 쥐를 알아챔(시야·거리) → "!" → 추격 → 숨으면 놓침 |
| 게임 시스템 | 체크포인트 5개, 페이드 리스폰, 빵 부스러기·황금 크루아상 수집, 별점 3개, 완료 패널, 재시작 |

| 품질 관리 | Validator 메뉴(중복 Provider, 입력 바인딩, 비네트 연결 등 점검), "미검증" 표기 원칙, 상세 개발 문서 |

### 현재 상태
- **블록아웃 프로토타입**이다. PC 에디터에서 텔레포트 방식으로 주요 기능을 부분 검증했다(NEXT_STEPS 1-2절). **Quest 실기기와 처음부터 끝까지 실제 조작한 플레이는 아직이다.**
- 이번 AI 리뷰에서 나온 문제 25건 중 **P0(실행 불가)은 0건**이다. 핵심 경험을 해치는 P1은 10건으로, 주로 **추격 밸런스, 주방 낙하 멀미, 실패 피드백, 온보딩**이다.

### 발표 때 말하면 좋은 "다음 단계"
1. 추격 밸런스와 "숨을 곳 안내" 다듬기 → 실제 플레이테스트로 검증
2. 멀미 대책: 낙하·달리기 비네트, 편안함 모드
3. 실기기 빌드(Quest 3)와 72fps 측정
4. 무료·라이선스 확인된 에셋으로 블록아웃 교체 (`docs/NEXT_STEPS.md` 3절)

## 1. Executive Summary

### 전체 평가
기술 기반은 탄탄하다. 이동 경로 하나, 카메라 비개입, 페이드 리스폰, 편안함 설정 에셋, Validator, 미검증 표기까지 VR 프로토타입으로서는 설계 원칙이 분명하다. 반면 **콘텐츠 밸런스와 피드백 층**이 기술 기반을 따라가지 못한다. 추격자는 쥐가 낼 수 있는 어떤 속도보다 빠른데 숨을 곳을 알려 주지 않는다. 실패 이유가 제대로 전달되지 않는다. 주방에서는 체감 9m 낙하가 아무 완충 없이 일어난다. 중간발표 시연 관점에서는 **입문자가 첫 1분 안에 이유를 모른 채 실패할 가능성**이 가장 큰 위험이다.

### 테스트 범위
- 페르소나 5명(입문자, VR 경험자, 게임 숙련자, 멀미 민감자, 핵심 타깃) × 사용자 흐름·예외 상황 테스트, 인터뷰 5건
- 구조·협업(P2 담당), 기기 성능(P4 담당, 잠재 위험만), 멀미·편안함과 추격 난이도는 전원 공통 중점
- 서브에이전트가 제기한 주요 주장은 오케스트레이터가 코드로 다시 확인했다 (5절 끝 "교차 검증 기록")

### 핵심 발견
1. **추격은 숨기만이 답이다.** 추격 속도 0.55~0.6 m/s > 쥐 최고 속도 0.5(질주, 상한에 잘림) > 달리기 0.36 > 걷기 0.2. 약 0.85m 안에서 들키면 숨지 않는 한 1.6~3초 안에 밟힌다. 그런데 들켰을 때 숨을 곳을 짚어 주는 장치가 없고, 화살표는 계속 경로(빗자루 구간에서는 추격자 쪽)를 가리킨다.
2. **주방 낙하 멀미.** 폭 15cm 널빤지와 높이 0.3/0.6/0.9m 상자에서 떨어지면 체감 3~9m를 0.8~1.4초 동안 비네트나 페이드 없이 떨어진다. 낙하가 실패로 처리되지도 않는다.
3. **실패 피드백이 약하다.** 실패 문구는 "밟힐 뻔했어요!"로 실제 결과와 반대이고, 원인을 구분하지 않는다. 메시지 칸이 하나라 부스러기 손실 메시지 등에 바로 덮인다.
4. **온보딩.** 조작 안내는 스틱을 밀면 약 1.9초 만에 사라지고 다시 볼 수 없다. 시작 지점 바로 앞(0.7m)이 웨이터 A의 순환 경로이고, 첫 부스러기와 힌트가 그 경로 위에 있다.
5. **HUD 위치.** 시야 아래 안내판이 쥐 발 기준 +2cm 높이라 배경 아래쪽이 늘 바닥 밑에 있고, 경사 널빤지에서는 통째로 묻힐 수 있다.

### 가장 중요한 개선 과제 5개
| 순위 | 과제 | 관련 문제 |
|---|---|---|
| 1 | 추격 밸런스 조정 + 들켰을 때 가장 가까운 안전 구역 안내(화살표 전환·바닥 강조) + 힌트 문구 정정 | ISSUE-01, 09 |
| 2 | 주방 낙하 완충(공중 비네트 기본 켜기, 큰 낙하는 페이드 후 직전 지점 복귀, 널빤지 폭 확대·턱 추가) + 달리기 비네트 | ISSUE-02, 03 |
| 3 | 실패 원인별 문구와 메시지 큐, HUD를 시선 높이로 올리기 | ISSUE-05, 04 |
| 4 | 시작 구간 정리: 안내를 다시 볼 수 있게, 첫 20~30초는 웨이터가 시작 구역에 오지 않게 | ISSUE-06, 07 |
| 5 | 시연 빌드 준비: OpenXR·XR 설정 커밋, Quest URP 최적화 필수화, 빗자루 이벤트 재준비 순서 문제 수정 | ISSUE-20, 21, 08 |

## 2. 프로젝트 분석
자세한 내용은 `reports/01-project-analysis.md`.

- **핵심 기능**: 쥐 시점 이동, 발걸음 회피, 숨기, 사람의 인지·추격, 수집과 별점, 체크포인트 리스폰
- **주요 Scene**: `PetitParisVR`(게임), `PetitParisSandbox`(조작 테스트). 둘 다 레포에 없고 에디터 메뉴로 생성한다
- **사용자 흐름**: 벽 틈 시작(CP0) → 카페 테라스(웨이터 A, CP1) → 빵집 앞(셰프 B·바게트, CP2) → 골목(자전거·빗자루 추격, CP3) → 센강(CP4) → 주방(요리사·널빤지) → 식탁 위 치즈 → 완료 패널 → A로 재시작
- **기술 구성**: Unity 6000.6.9f1, URP 17.6, XRI 3.6.1, Input System 1.20.1. C# 약 9,100줄. 외부 에셋 없음

- **발생 상황**: 보행자에게 들킨 뒤(발견 반경 1.0~1.1m, 시야 ±65°, 0.2m 안이면 각도 무관)
- **재현 방법**: 테라스에서 웨이터 A 정면 0.7m에 선다 → "!" 후 0.9초 → 추격 시작 → 달리기로 직선 도주

## 9. 개선 실행 계획

### 즉시 수정 (중간발표 전, 각 수십 분~1시간 규모)
1. `PetitParisText.MessageDied` 문구 정정 + `reason`별 문구 (ISSUE-05)
2. `RatComfortSettings` 기본값: `vignetteInAir = true`, 달리기 비네트 추가 (ISSUE-02, 03)
3. 힌트 문구 4개 정정 (ISSUE-09)

7. 안전 구역 이름을 `PetitParisText`로 이동 (ISSUE-23)
8. README·CLAUDE.md 목적지 갱신 (ISSUE-22)

### 단기 개선 (1~2주)

### 실제 사용자에게 물어볼 질문
1. 처음 10초 동안 무엇을 해야 한다고 생각했나요? 어떤 버튼을 먼저 눌렀나요?
2. 실패했을 때 무엇 때문인지 알았나요? 어디서 알았나요?
3. 사람이 쥐를 알아챘을 때 어떻게 알았나요? 어디로 가야 할지 알았나요?
4. 어지럽거나 불편했던 순간이 있었나요? 정확히 어떤 장면이었나요? (0~10점)
5. 쥐가 된 느낌을 가장 크게 준 순간은 언제였나요?
6. 시야 아래 글자(점수·메시지)를 봤나요? 손목 패널은요?
7. 센강에 도착했을 때 무슨 생각을 했나요?

### 추천 테스트 시나리오
- **S1 첫 1분(입문자)**: 설명 없이 시작 → 테라스 첫 체크포인트까지. 사망 횟수, 첫 질주·첫 숨기 시점 기록
- **S2 추격 대응**: 테라스에서 일부러 들키게 유도 → 숨기 성공 여부·시간
- **S3 멀미**: 앉은 자세로 전체 플레이 → SSQ 전후, 주방 구간 낙하 횟수
- **S4 전체 완주(핵심 타깃)**: 완주 시간, 별 개수, 센강에서의 반응
- **S5 시연 환경**: 학회 부스처럼 진행자 1명·대기 인원이 있는 상태에서 1인당 소요 시간 측정

### 검증 성공 기준 (예시)
- 입문자 80% 이상이 진행자 도움 없이 첫 체크포인트 도달
- 실패 직후 원인 질문 정답률 80% 이상
- 들킨 뒤 숨기 성공률 60% 이상 (조정 후)
- SSQ 총점 상승이 경미 수준, 중도 포기 0명
- 핵심 타깃 완주 시간 중앙값 5분 이하

## 11. 테스트 한계

| 항목 | 내용 |
|---|---|
| 정적 분석 범위 | 런타임 스크립트는 오케스트레이터가 핵심 대부분을 직접 읽었고, 서브에이전트가 나머지와 빌더를 필요한 만큼 읽었다. ParisKit·Textures·셰이더 본문은 거의 보지 않았다 |
| 실제 실행 여부 | **실행하지 않음.** Unity 컴파일·Play·Console 확인 없음. 추격·낙하 시간은 코드 수치로 계산하고, 일부는 Python 단순 모델로 추정함(P3·P5). CharacterController 가장자리 동작, 실제 프레임 시간은 반영하지 못함 |
| XR 기기 테스트 | **하지 않음.** 멀미·크기감·가독성·음향 방향은 모두 추정 |
| 씬 상태 | 씬 파일이 레포에 없어 빌더 코드의 기본값으로 판단했다. 사용자가 Inspector에서 바꾼 값이나 씬에 저장된 실제 값은 반영하지 못했다 |
| 페르소나 | 가상 인물이다. 실제 사용자의 행동 분포를 대신하지 못한다. 인터뷰 답변은 코드 근거를 바탕으로 한 가상 응답이다 |
| 검증하지 못한 항목 | 72fps, 한글 렌더링, Touch Plus 버튼, 재중심·포커스 OS 동작, 비네트 샘플 기본값, 3D 음향 앞뒤 구분, 실제 난이도 체감 |
| 리소스 사용 | 승인한 Standard 예산(약 0.56~0.9M 토큰)을 **넘었다.** 서브에이전트 5개가 약 1.41M 토큰(보고값 합계)을 썼고, 오케스트레이터 사용분을 더하면 전체 약 1.6~1.8M으로 추정된다. 페르소나 테스트 단계를 30~50만 토큰으로 잡았는데, 각 에이전트가 코드를 독립적으로 다시 읽으면서 약 3배가 들었다. 중간에 예산 초과를 감지해 멈추지 못했다(서브에이전트가 병렬로 동시에 끝남) |
